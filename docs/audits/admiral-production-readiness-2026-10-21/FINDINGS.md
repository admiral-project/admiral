## ADM-F-038 — Removed worker retains a trusted WireGuard peer ([#272](https://github.com/admiral-project/admiral/issues/272))

**Status:** Reproduced on exact R72 packages in AlmaLinux 10 and CentOS Stream 10 three-guest Multi-Node runs. The fix is in Release 73 (`admirald@83b4dd4db8963ac40a51c00fb9e52a9f2081df5c`); component CI [40080443575](https://github.com/admiral-project/admirald/actions/runs/40080443575) passed. Exact-RPM R73 checks passed on Rocky, AlmaLinux and CentOS Stream: active-worker removal was rejected and preserved the workload; idle removal removed the node and its live/persistent WireGuard peer. On each OS, the removed worker could not reach the tested private UI endpoint (timeout, HTTP `000`). On AlmaLinux, the removed worker's old Fleet token returned HTTP 401 after a temporary VPN route was restored solely to isolate authorization; that temporary peer was removed and verified absent. The R73 CentOS check separately submitted the former token from the hub after removal and got HTTP 401. Real post-removal hub reboots on all three EL10 systems kept the removed node record and peer absent; the remaining worker's route, fresh handshake and heartbeat returned. A controlled helper failure on AlmaLinux and CentOS Stream returned HTTP 503 while retaining the active worker record, unchanged token fingerprint, and live/persistent peer; restoring the packaged helper allowed retry to remove node/token/peer and securely re-enroll. Secure same-guest re-enrollment passed on all three OSes. Revalidation on Fedora, helper-failure rollback/retry on Rocky, broader private-service reachability and cross-OS regression remain outstanding. Issue #272 stays open.

* **Severity:** MEDIUM — the former Fleet token was rejected with HTTP 401, but the removed worker remained a cryptographically trusted WireGuard peer and could reach the private admin UI listener.
* **Component:** `admirald` node deletion, Admiral common package, and hub WireGuard peer lifecycle.
* **Environment:** RC5 Release 72 (`0.0.1rc5-72.el10`), AlmaLinux 10 and CentOS Stream 10 x86_64, secure three-guest Multi-Node clusters.
* **Reproduction:** Install a hub and two workers, deprovision W2, remove it through `admiralctl nodes remove`, then inspect the hub's live `wg-admiral` allowed IPs and persistent WireGuard files. From W2, attempt the hub's private UI and a Fleet request with the old token without printing the token.
* **Expected:** Active-worker removal remains HTTP 409 and preserves workloads. Idle-worker removal removes its database record/token and peer from live and persistent hub state; the removed worker cannot reach protected hub services, including after hub reboot.
* **Observed:** The node record and token were deleted, and the Fleet request returned HTTP 401, but the removed worker's `/32` remained in the live interface and persistent files. The worker still reached `https://10.99.0.1:5001/` with HTTP 200. This was reproduced on AlmaLinux and CentOS Stream R72.
* **Evidence:** R72 AlmaLinux raw capture under ignored `packaging/build/validation/rc5-r72/runtime/artifacts/alma-mn/node-removal-w2-retry1/`; CentOS Stream capture under `packaging/build/validation/rc5-r72/runtime/artifacts/centos-mn/node-removal-w2/wireguard-residual/`. R73 Rocky captures are under `packaging/build/validation/rc5-r73/runtime/multi/rocky/node-removal-w2-run2/`; AlmaLinux captures and manifest hashes are in [`release73-alma-multinode-progress.md`](evidence/release73-alma-multinode-progress.md). Reproduction scripts are tracked under [`evidence/scripts/`](evidence/scripts/).
* **Root cause:** Confirmed by code inspection: node deletion removed database/token state but did not revoke the WireGuard peer. The persistent hub files and running interface therefore continued to trust the worker.
* **Recommendation:** Revoke the live and persistent peer before committing node/token deletion. Keep the daemon unprivileged, make the helper fail closed, serialize peer addition/removal, and retain the node/token when revocation fails so an operator can retry.
* **Regression:** On fresh R73 three-guest clusters, test active-worker refusal, successful idle-worker removal, absence from live and persistent peer state, rejected old token, failed-helper response with retained DB/token followed by successful retry, hub reboot with no peer restoration, no access to the private hub UI, and continued health of the hub/remaining worker. Run on all four OSes; do not credit R72 evidence.

## ADM-F-036 — Active-instance node removal returns HTTP 500 instead of conflict ([#267](https://github.com/admiral-project/admiral/issues/267))

**Status:** R68 exact-candidate regression **PASS, scoped on AlmaLinux 10.2 Multi-Node**. Issue #267 remains open with `fix-proposed`; this result verifies the reported behavior only on AlmaLinux and is not a complete cell or a reason to close the issue. Matrix remains 0/8.

* **Severity:** MEDIUM.
* **Component:** `admirald` node-removal handler/database error contract and `admiralctl` node-removal command/client retries.
* **Environment:** RC5 Release 68 (`0.0.1rc5-68.el10`), AlmaLinux 10.2 x86_64, real three-guest Multi-Node topology. Test ID `R68-ALMA-MN-NODE-REMOVE-01`.
* **Reproduction:** Provision `e2e-whoami` on W2; verify API state `running/healthy/available` and HTTP 200. Invoke `admiralctl nodes remove <W2>` without `--force` and answer `y`.
* **Expected:** Return HTTP 409 once, explain the active-instance conflict and preserve the node and workload registration until an explicit safe action is taken.
* **Observed on R68:** The authenticated API returned HTTP 409 once with the active-instance count and `--force` guidance. `admiralctl nodes remove` exited 1 with the same guidance and no HTTP 500/retry exhaustion. The instance remained `running/healthy/available` and returned HTTP 200 after the rejected removal. Deprovision succeeded, the worker had no matching containers, pods, volumes or files, and idle-node removal removed the node from inventory.
* **Evidence:** [`release68-alma-multinode-node-removal.md`](evidence/release68-alma-multinode-node-removal.md), [`r68-alma-multinode-node-removal.sh`](scripts/r68/r68-alma-multinode-node-removal.sh), and the verified local mode-0600 evidence manifest (SHA-256 `67ecaf922ef62bbf8110beac580d56b16d046ebcaf3ceadb5b0eabb3468ce67a`). Raw files are retained under ignored `packaging/build/validation/rc5-r68/alma-mn-node-removal/run/`.
* **Root cause:** Confirmed. The database error contained `has 1 active instance(s)`, while the handler searched for the exact substring `has active instance`. The count prevented classification as HTTP 409, so the handler returned 500. The CLI force-removal hint had the same overly specific match and was skipped.
* **Recommendation:** Use a typed database sentinel for the active-instance condition; map it to HTTP 409 and print guidance based on the structured conflict. Do not retry permanent client errors.
* **Regression test:** Passed on the exact R68 candidate for AlmaLinux as recorded above. Repeat the regression on Fedora Rawhide, Rocky Linux 10 and CentOS Stream 10, and test active-task cancellation/compensation before claiming Multi-Node cell completion. Same-guest re-enrollment after removal passed as a separate AlmaLinux R68 check. Keep #267 open until its tracker acceptance and cross-OS matrix evidence are dispositioned.

Source fixes: `admirald@a4d39ae6b5db92bd7e6e5257dc8f6b919af52668` and `admiralctl@fa2a65e866310bd82bea78859804b6c3aea7989a`. Full component test suites and `go vet` passed locally. Upstream CI passed for [`admirald`](https://github.com/admiral-project/admirald/actions/runs/40030035439) and [`admiralctl`](https://github.com/admiral-project/admiralctl/actions/runs/40030034925). The exact R68 `.el10` candidate passed the AlmaLinux regression described above; cross-OS reproduction and full-cell evidence remain pending. #267 remains open.

## ADM-F-035 — Fresh Fedora Multi-Node workers fail before baseline package installation ([#266](https://github.com/admiral-project/admiral/issues/266))

**Status: R67 scoped fresh-bootstrap regression PASS; full Multi-Node cell and teardown remain pending.** The source correction is pushed in root commit `ad4f6caa0572ebeff54d3dfcb51f635cf346b31e`; its root CI run [39967404421](https://github.com/admiral-project/admiral/actions/runs/39967404421) succeeded. Two fresh Fedora R67 workers completed secure bootstrap, resolver checks, registration, heartbeat and WireGuard verification with zero failed/unreachable tasks. Issue #266 remains open with `fix-proposed`; Release 66 is invalidated for active matrix credit; matrix remains 0/8.

* **Severity:** HIGH.
* **Component:** `admiral-common` installer role and RPM-owned systemd resolver directory.
* **Environment:** Fresh Fedora Rawhide x86_64 secure Multi-Node W1 and W2, using the R66 candidate.
* **Reproduction:** On a fresh Fedora worker, configure the exact Fedora candidate repository and run the supported `admiral-install --worker-node` bootstrap. Both R66 workers fail at `Disable LLMNR on Fedora secure installs` before `admiral-common` is installed.
* **Expected:** The exact candidate completes worker bootstrap; LLMNR is disabled, unicast DNS works, the worker obtains a fresh heartbeat and WireGuard handshake, and the temporary bootstrap credential is revoked.
* **Observed:** Both fresh workers exit nonzero with `Destination directory /etc/systemd/resolved.conf.d does not exist`; recap is `ok=12 changed=0 unreachable=0 failed=1`. Neither worker reaches Admiral package installation, Fleet registration, or WireGuard startup. The R66 hub succeeded because its `admiral-common` RPM already owned the directory.
* **Evidence:** R66 raw worker logs are preserved mode `0600` on the isolated validation host: W1 SHA-256 `2b9765a8733c34020ad24f109c9ab77376be1c1dfc31a3a8550687003f1289d0`; W2 SHA-256 `710f2fdbfb59b2b89c47caee1b1403cd6bc87ad526e529ac20d903b86331887a`. Exact issue reproduction and root-cause notes are in [#266](https://github.com/admiral-project/admiral/issues/266).
* **Root cause:** Confirmed task-ordering defect: Fedora resolver policy writes a drop-in under `/etc/systemd/resolved.conf.d` before the later `Install admiral-common baseline package` task. The RPM spec owns this directory. This is separate from #126, which fixed the LLMNR policy but not fresh-worker task ordering.
* **Recommendation:** Install the baseline RPM before applying the resolver drop-in; keep fixed directory ownership and permissions in the RPM spec and do not create that directory in Ansible.
* **Regression test:** On the exact R67 candidate, a fresh Fedora hub and two fresh worker overlays completed secure installation. The baseline package preceded resolver hardening on both workers; `resolvectl` showed `-LLMNR`, no UDP/TCP 5355 listener was found, unicast DNS resolved the COPR host, the hub reported two active/healthy workers with current heartbeat/metrics, and WireGuard handshakes were present. Both bootstrap helpers verified their temporary keys no longer authenticated. Hub recap was `ok=245 changed=107 unreachable=0 failed=0`; each worker recap was `ok=157 changed=54 unreachable=0 failed=0`. Full evidence and raw-log hashes: [`release67-fedora-multinode-bootstrap.md`](evidence/release67-fedora-multinode-bootstrap.md); postcheck log SHA-256 `0cd8b138c9b11067cc419a32463e475ac5cefe8d3232abd6901dd5df3abe826e`. A subsequent separate R67 scenario passed workload lifecycle on both workers; see [`release67-fedora-multinode-placement.md`](evidence/release67-fedora-multinode-placement.md). The bootstrap regression itself did not test partition, recovery, conflicting concurrency, isolation or stress; do not count a matrix cell. Keep #266 open and do not carry this scoped result into other OSes.

## ADM-F-001 — Repeating provision could create an unintended second instance ([#207](https://github.com/admiral-project/admiral/issues/207))

**Status: RESOLVED UPSTREAM; issue #207 was already closed before these R67 runs.** The historical reproductions below describe the pre-fix candidate. R66 same-key replay passed on all four Single-Node OSes, and concurrent identical same-key requests returned the same operation and instance on AlmaLinux and CentOS Multi-Node. R67 then released three simultaneous same-key requests on the exact candidate in both AlmaLinux and CentOS; R68 repeated the three-client race on the exact candidate on AlmaLinux. Each tested release returned one operation/task/instance and one runtime resource set, reached healthy/available and HTTP 200, and cleaned up the workers. See [`release67-alma-multinode-concurrent-idempotency.md`](evidence/release67-alma-multinode-concurrent-idempotency.md), [`release67-centos-multinode-concurrent-idempotency.md`](evidence/release67-centos-multinode-concurrent-idempotency.md) and [`release68-alma-multinode-concurrent-idempotency.md`](evidence/release68-alma-multinode-concurrent-idempotency.md). These are scoped regression results, not full concurrency validation.

* **Severity:** MEDIUM.
* **Component:** `admirald` instance API and `admiralctl` provision command.
* **Environment:** Confirmed sequentially on AlmaLinux 10.2, Rocky Linux 10.2, Fedora Rawhide and CentOS Stream 10 x86_64 Single-Node; confirmed concurrently on Fedora Rawhide and CentOS Stream x86_64 Multi-Node. The instance creation path is shared by both topologies.
* **Reproduction:** Apply `examples/apps/e2e-whoami.yaml`; run `admiralctl instances provision --app e2e-whoami --tier small --customer audit_alma_20261021 --wait --quiet --output json` twice with the same arguments, or submit concurrent requests for the same app/customer. Compare returned instance IDs and Podman resources. Fedora Multi-Node requests to one worker both succeeded with separate IDs and six containers. In CentOS Stream Multi-Node, requests for the same app/customer began 22.9 ms apart while targeting separate workers; both succeeded with instance IDs `inst_de21f056551792b1` and `inst_42609b8fb15431a0`. The CentOS Stream Single-Node repeat created `inst_2367aa6459d1a295` with operation `op_4ce681ce8ab3ce84`. All duplicate test instances were deprovisioned and their container, volume and Quadlet state was verified clean.
* **Expected:** An explicit replay of an operation after an ambiguous timeout can return the original operation/result, or require a stable idempotency token that prevents duplicate billable resources.
* **Observed on pre-fix candidates:** Two distinct successful instances were created for ambiguous duplicate requests. The fix added an `Idempotency-Key` contract and persisted replay lookup; R66 tests with the same key converged on one operation and instance. On R67 AlmaLinux and CentOS Multi-Node, three same-key requests each returned one operation/task/instance and one workload resource set; each API moved from a conservative unavailable startup sample to healthy/available and HTTP 200. Requests with different keys intentionally remain distinct operations.
* **Evidence:** `evidence/alma-single-execution.md` test `ALMA-SN-005`; `evidence/fedora-multi-concurrent-provision.md`; `evidence/centos-single-execution.md` test `CS-SN-005`; direct cross-worker reproduction `evidence/centos-multi-execution.md`; [`release67-alma-multinode-concurrent-idempotency.md`](evidence/release67-alma-multinode-concurrent-idempotency.md); and [`release67-centos-multinode-concurrent-idempotency.md`](evidence/release67-centos-multinode-concurrent-idempotency.md). Restricted raw logs are ignored and mode `0600`; no credentials are committed.
* **Root cause:** Historical design gap, corrected upstream by persistent caller idempotency and replay semantics.
* **Recommendation:** R68's AlmaLinux race did not reproduce duplicate work for the tested same-key request. Continue testing timeout-after-commit, token scope, conflicting-body rejection, cross-node mutation races and distinct-key intent in the full matrix.
* **Regression test:** R66 replay passed across four Single-Node OSes; R66 same-key concurrent replay passed on AlmaLinux/CentOS Multi-Node; R67 three-request replay passed on both EL10 Multi-Node topologies. Timeout-after-commit, conflicting same-key request bodies, cross-customer scope and distinct-key behavior remain untested in live guests.

## ADM-F-002 — Instance API health remains last-known healthy while its worker is offline ([#208](https://github.com/admiral-project/admiral/issues/208))
**R67 scoped regression:** On all four OS three-guest candidates, W2 became unavailable/offline during an isolated WireGuard partition and returned active/healthy/available after peer restoration. HTTP and SQL data persisted and deprovision cleanup passed. This is a named regression result only; no in-flight task/callback behavior or complete matrix cell was tested. Evidence: [`release67-fedora-multinode-targeted.md`](evidence/release67-fedora-multinode-targeted.md) and the Rocky, AlmaLinux and CentOS Stream R67 reports. #208 remains closed upstream; no issue status was changed by this audit.


* **Severity:** MEDIUM.
* **Component:** `admirald` node health monitor and instance status API/UI consumers.
* **Environment:** Historical failures confirmed on AlmaLinux 10.2, Rocky Linux 10.2 and CentOS Stream 10 x86_64 three-node Multi-Node labs. R66 exact-candidate packet-partition regressions were subsequently run on AlmaLinux and CentOS Stream. GitHub currently marks #208 closed with `fix-confirmed` and `fixed` labels.
* **Reproduction:** Provision an instance on a worker. Suspend it with `virsh suspend <worker-domain>` or, on the isolated Rocky lab hub, drop packets with `nft add rule inet admiral_audit_partition input iifname enp2s0 ip saddr 10.77.0.11 drop`. Wait for the hub to mark it offline, then query `admiralctl nodes list` and `admiralctl instances list/show` before restoring traffic or resuming.
* **Expected:** Consumers can distinguish a currently available/healthy instance from the last state observed before its worker became unreachable.
* **Observed:** Historical AlmaLinux, Rocky and CentOS runs showed `offline/degraded` nodes while assigned instances retained `running/healthy` with pre-outage health timestamps. On exact R66, AlmaLinux and CentOS W2 partition tests instead reported effective instance availability as `unavailable`. In the corrected CentOS run, that transition was observed by ~16 seconds with reason `runtime_observation_stale`; the node became `offline/degraded` at 140 seconds with `heartbeat_timeout`. After restoring the peer, node and instance returned to active/healthy/available within ~13 seconds. HTTP and SQL data persisted and cleanup succeeded. No task was in flight, so callback/lease replay was not tested.
* **Evidence:** Historical evidence: `evidence/alma-multi-execution.md`, `evidence/rocky-multi-partition.md` and `evidence/centos-multi-execution.md`. Exact R66 regressions: `evidence/release66-alma-multinode-targeted.md` and `evidence/release66-centos-multinode-targeted.md`; corrected CentOS mode-0600 local manifest SHA-256: `3396a8d13a2013d72349398566fd5c7a9df59bcdb7e7049f0137d0717fb41fe0`.
* **Root cause:** Confirmed in the pre-fix behavior: the offline monitor updated the node record without changing or annotating instances assigned to that node. R66 regression runs show effective-availability propagation on the tested paths; this does not establish task/callback semantics or full-matrix coverage.
* **Recommendation:** Expose an effective instance availability/health state derived from node reachability while preserving the last runtime observation as a separate field. Restore current state after heartbeat and health checks return.
* **Regression test:** The targeted worker-partition regression passed on exact R66 AlmaLinux and CentOS Stream candidates. Keep the automated matrix regression covering stale health, offline threshold, rejoin, last-known timestamps and in-flight task/callback behavior across the remaining OS/topology cells.

## ADM-F-003 — Historical Go HTTP/2 denial-of-service advisories in the control-plane build ([#209](https://github.com/admiral-project/admiral/issues/209))

**Status: RESOLVED for Release 66; issue #209 is closed upstream.** The finding was real on Release 42, whose binaries used Go 1.26.7 and `golang.org/x/text v0.40.0`. Release 66 now has exact RPM, source scan and Multi-Node runtime evidence for the fix. The Release 42 observations remain historical and must not be attributed to the current candidate.

* **Historical severity:** HIGH.
* **Component:** Go HTTP/2 implementation in `admirald`; the same Go standard library is present in `admiral-fleet` and `admiralctl`.
* **Environment:** Historical Release 42 issue was reachable from an enrolled Multi-Node worker. Exact Release 66 was checked on EL10 x86_64.
* **Historical reproduction:** Install the Release 42 candidate. `govulncheck v1.9.0` in `admirald` reported 11 reachable advisories, including `GO-2026-6617` and `GO-2026-6603`; installed `/usr/bin/admirald` reported Go `1.26.7` and VCS revision `748b703662eafdaf3919bad28787d0264f06bf16`. From an enrolled worker, `curl --http2 -k -sS -o /dev/null -w '%{http_version} %{http_code}' https://10.99.0.1:8080/api/v1/status` negotiated HTTP/2 and received 401.
* **Expected:** Packaged binaries use fixed standard-library and direct-module versions; source scans show no reachable advisories; an unauthenticated peer request receives 401.
* **Observed:** Release 42 had reachable Go standard-library and `x/text` advisories. For exact Release 66, all three RPM binaries report Go 1.26.10; `admirald` reports `x/text v0.41.0`; `govulncheck v1.9.0` returned exit 0 with no reachable findings for all three exact source modules. From a connected CentOS Stream R66 worker, the hub negotiated HTTP/2 and returned 401. No malicious frame sequence was sent.
* **Evidence:** [`release66-go-security-verification.md`](evidence/release66-go-security-verification.md); historical scan: [`go-dependency-scan.md`](evidence/go-dependency-scan.md). Scanner database snapshot last updated 2026-10-21.
* **Root cause and resolution:** Release 42 used stale Go and `x/text` versions. R66 component pins use Go 1.26.10 and `x/text v0.41.0`; source scanning and runtime authentication-boundary checks passed.
* **Regression test:** Inspect binary metadata and run `govulncheck` on all three modules for each coordinated candidate. This finding is resolved for R66, but does not establish full security readiness or complete a matrix cell.

## ADM-F-005 — Hub restart does not restore durable WireGuard peer fragments ([#211](https://github.com/admiral-project/admiral/issues/211))
**R67 scoped regression:** All four OS Multi-Node hub reboots restored worker routes/handshakes and active workload HTTP/SQL state. Fedora recovered at poll 2 (~58 seconds), Alma at poll 2 (~70 seconds), CentOS at poll 3 (~81 seconds), and Rocky's stricter follow-up required fresh post-reboot worker heartbeats. This is not a full Multi-Node cell or cross-OS guarantee. #211 remains open; no issue was closed. Evidence: the four per-OS R67 Multi-Node reports.


**R66 status:** targeted hub reboot/rejoin passed on AlmaLinux and CentOS Stream three-guest labs. In both, the two configured/runtime peers and handshakes returned, workers became active/healthy without rerunning Ansible, and an active workload retained its SQL marker and returned HTTP 200. See [`release66-alma-multinode-targeted.md`](evidence/release66-alma-multinode-targeted.md) and [`release66-centos-multinode-targeted.md`](evidence/release66-centos-multinode-targeted.md).

* **Severity:** HIGH.
* **Component:** Multi-Node hub WireGuard configuration and worker connectivity.
