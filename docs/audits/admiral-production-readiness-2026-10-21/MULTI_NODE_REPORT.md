## Topology correction — R75 Multi-Node evidence is invalid for the release gate

The required Multi-Node roles are `--admin-node`, `--worker-node`, and an
independent `--portal-node`. R75 used `--admin-portal-node` plus workers.

observations only and receive **no cell credit**. In particular, they did not
validate independent Harbor installation, WireGuard API access, portal routing,
or customer workflows. The RC6 Multi-Node matrix is **0/3 PASS** until these
three-node topologies are run against the exact candidate.

## R68 AlmaLinux 10.2 three-client idempotency race — scoped

Three synchronized clients issued the same provision request with one idempotency key on the real three-guest R68 AlmaLinux cluster. All returned the same successful operation, task, instance and W1 assignment; the customer had one active instance and W1 held exactly one three-container runtime set. W2 had no matching resources. The instance health moved from a conservative stopped/unavailable snapshot to healthy/available, HTTP returned 200, and deprovision removed all worker runtime resources. Both workers remained available. The request race took 32.13 seconds; detailed timestamps, IDs, state snapshots, the retained deprovisioned audit row, reproduction steps and hashes are in [`release68-alma-multinode-concurrent-idempotency.md`](evidence/release68-alma-multinode-concurrent-idempotency.md).

The health transition matches the documented `--wait` contract tracked in #236: operation terminality precedes asynchronous runtime-health convergence. The test waited for health before accepting the workload result and required HTTP 200. This is a scoped same-key regression only, not broad concurrency or a cell PASS. The first auxiliary postcheck's assumption that deprovision erased the customer history was incorrect; the retained row is `deprovisioned/cancelled`, while runtime inventories are empty. The failed assertion is preserved and excluded from the result.

## Observed architecture and guarantees

The deployed model is one control-plane hub plus N worker spokes, not a replicated cluster. SSH/Ansible bootstraps nodes; WireGuard carries internal traffic. `admirald` and central PostgreSQL own global state. Workers execute signed, leased tasks through Fleet and report authenticated callbacks. Node health monitoring marks worker nodes offline after a 2-minute heartbeat threshold (observed transition can take up to the threshold plus the 30-second monitor tick). The hub and database remain single points of failure.

The durable queue uses lease-based at-least-once delivery. No exactly-once guarantee was found. A disconnected worker does not receive current tasks or report results. There is no quorum, multi-hub failover, automatic workload migration, or automatic recovery on a replacement worker. A workload remains assigned to its original worker until an operator performs a separately audited action.

## Historical R67 operational limits

Loss of the hub or central database blocks new control-plane operations and callbacks; this is a single-hub/single-database architecture, not HA. Workers may keep already-running local workloads under systemd, but the hub cannot authoritatively coordinate while disconnected. A worker loss interrupts workloads placed there; automatic migration is not implemented. Historical releases showed stale instance health during worker outages (`ADM-F-002` / #208). R67 targeted runs on AlmaLinux and CentOS Stream reproduced the documented offline/rejoin transitions; their R67 hub reboots recovered peers/workers, injected Podman delete errors remained visible until retry, and central PostgreSQL outages recovered (#264). On CentOS, the controlled outage produced 78 Fleet 503s, zero 401/429, preserved HTTP 200 and SQL data, and both workers recovered. These scoped passes now cover selected scenarios on all four Multi-Node targets but do not establish full readiness. Placeholder-secret rejection (`ADM-F-007`), S3/volume restore, callback/lease replay, and WireGuard identity backup remain unvalidated.
