# RC6 Epoch 4 / Release 2 — corrected Harbor prepaid-expiry reproduction

**Result: the #295 denial did not reproduce with a Harbor-generated customer identity and Harbor's packaged API client.** This is a focused issue check on a diagnostic Epoch build, not a release-matrix cell. No source-code fix was made.

## Candidate and environment

- Fedora Rawhide 46 x86_64 KVM guest `rc6e4f190retry`.
- Six native Fedora packages: `Epoch 4`, `0.0.1rc6-2.fc46`.
- RPM SHA-256 values are in `fedora-rpm-manifest.tsv`; package versions and test timestamps are preserved in `install.log` and `worker.log`.
- Installed Harbor code is from submodule `admiral-harbor` commit `dd4818b6e2bc53eea4495fc5e374a4893cfcb107`.
- The worker is the packaged `admiral-harbor-worker.service`, run as `admiral` with `/etc/admiral/harbor.env`.

## Procedure

1. Applied the local `e2e-whoami` app definition to Admirald.
2. Registered a disposable Harbor account through `/auth/register`; Harbor generated customer ID `hcus_f2c4057cd89a485f`. The test fixture was then approved locally as an administrator would approve a pending signup.
3. Provisioned the workload using Harbor's installed `provision_app` API client, with that generated customer ID. The installed Harbor client fetched the operation and read the instance using the same customer scope; both requests succeeded.
4. Seeded a cancelled prepaid subscription and matching local customer-app record with a future end date and `paypal_subscription_id=NULL`. No PayPal endpoint or sandbox was called.
5. Ran the packaged worker before expiry. The test instance remained `running`; no deprovision operation existed for it.
6. Advanced only the local test dates to the past and ran the packaged worker. It logged one deprovision operation, `op_1f5e9835331c869c`, with `Errors: 0`.
7. Verified the operation completed as `succeeded`, the instance reached `deprovisioned`, and a subsequent worker run created no second deprovision operation. The control-plane operation list contains exactly one deprovision operation for this instance.
8. Removed the Harbor fixture. The rootless Podman inventory was empty after deprovisioning.

## Evidence and interpretation

- The old #295 reproduction manually combined a CLI-provisioned instance and directly inserted Harbor rows. This corrected run uses a customer ID generated by Harbor and Harbor's real packaged provision/read/action client paths. It did not reproduce the 403.
- This evidence does **not** establish a product code fix or prove the cause of the earlier synthetic-fixture mismatch. It does show the earlier result is not sufficient to classify the production flow as a confirmed defect. Keep #295 open for review, remove `needs-work`, and mark it `posible-false-positive` pending triage; do not count it as a source fix.
- No PayPal behavior was exercised.
- No release matrix credit is awarded; formal matrix remains 0/6.
