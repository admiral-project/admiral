## Architectural conclusions recorded without changing checklist results

These conclusions resolve specific questions about the R26 design, but do not turn the corresponding original control into PASS:

1. **Published ports (B.12/I.8):** Quadlet intentionally publishes declared app ports on the Worker publish address. The code does not promise that only Caddy or the admin node can reach those endpoints. Whether a particular peer can reach one remains a runtime/network question.
2. **Volume naming (D.6):** private and shared volume names contain the instance identifier; the shared-volume contract is per instance. Naming evidence is not a test of effective mount ownership or of the supported shared-volume runtime mode.
3. **Node disable versus removal (I.4):** administrative disable sets a node state and recomputes policy; deletion follows a removal path that coordinates task cancellation and WireGuard peer revocation. A code path does not prove the peer is unreachable after the operation.
4. **Worker authorization (K.5/K.6):** the checks reject mismatched node identities, task assignments, inactive/expired node tokens, and revoked/expired operator tokens before the relevant handler proceeds. This is direct source evidence at authorization boundaries, not a live hostile-request result.

## Residual risks retained from the closed review

- **R1 — Podman `file` secret driver, MEDIUM residual:** the CentOS R26 probe recorded `effective_secret_driver=file`, which protects data using filesystem permissions but does not provide driver-level encryption at rest. The comments in [`renderSecretMounts`](https://github.com/admiral-project/admiral-fleet/blob/edc0a0d486eb102e9aaa4f250a08f777d7441f12/internal/quadlet/renderer.go#L327-L342) and [`createPodmanSecrets`](https://github.com/admiral-project/admiral-fleet/blob/edc0a0d486eb102e9aaa4f250a08f777d7441f12/internal/executor/executor_helpers.go#L375-L398) claiming encryption are not encryption evidence. Host-storage or snapshot access could expose the files; no cross-client secret access was demonstrated.
- **R2 — shared host account `admiral-apps`:** `UserNS=auto`, SELinux/MCS, and separate namespaces reduce cross-pod access, but compromise of the shared host account or root is outside the per-container isolation boundary. This documented launch-scope limitation is accepted by the owner.
- **R3 — incomplete adversarial/runtime coverage:** direct user-manager attempts, effective peer revocation, external IPv6 negatives, OOM behavior, and manipulated restore inputs were not all exercised. They remain PARTIAL/NOT TESTED, not presumed vulnerabilities and not presumed passes.
