## Decision

The R25→R26 product diff was reviewed and **no security regression was found**. The R26 evidence supports a reasonable baseline for the tested production topology: rootless Podman, `UserNS=auto`, per-pod namespaces and SELinux MCS, two real customer workloads on one Worker, and PostgreSQL backup/restore. This is a bounded conclusion for the controls and workload exercised; it is not a claim that every item in the broad A–L checklist has passed.

The only product change in this candidate is the Admirald resize/backup-policy fix. Its diff does not touch authentication, authorization, task signing, Fleet execution, secrets, Quadlet generation, Podman configuration, SELinux, Ansible, firewall, or WireGuard. The relevant routes still check customer ownership before queuing lifecycle or backup effects. The implementation details and exact SHAs are recorded in the [R26 regression review comment](https://github.com/admiral-project/admiral/issues/307#issuecomment-6483295945).

## Direct R26 evidence already collected

- **A/B isolation:** Two Harbor customers were deployed on the same Fedora Rawhide R26 Worker. Their rootless `auto` UID/GID ranges did not overlap (`720896+1024` and `721920+1024`); network/PID namespaces, MCS labels, volumes and secret paths were separate. A could not read or modify B's PostgreSQL volume or reach B's unpublished PostgreSQL port. Both routes returned HTTP 200 with strict TLS. See the [A/B runtime evidence](https://github.com/admiral-project/admiral/issues/307#issuecomment-6480994640).
- **Installer and rootless state:** The exact Fedora-native R26 packages completed Admin, Worker and Portal installation with zero failed or unreachable tasks. The packaged rootless check passed, and the Worker was configured with `userns=auto` and the selected subordinate ID pool. See the [installer evidence](https://github.com/admiral-project/admiral/issues/307#issuecomment-6481229798).
- **UserNS behavior:** The runtime ownership mapping differed between A and B, and cross-client persistent-volume access was denied. The measured ID pool and kernel limits exceed the documented 2,000-pod planning reference; that is a configuration calculation, not a hardware capacity claim. MariaDB/MySQL and full update/rebuild coverage were not exercised. See the [UserNS assessment](https://github.com/admiral-project/admiral/issues/307#issuecomment-6482113183).
- **Podman secret driver:** On the existing CentOS Stream 10 R26 Worker, a synthetic rootless secret reported driver `file`, which Podman documents as read-protected and not encrypted at rest. The secret was removed and its absence verified. This does not establish the effective driver on other OS cells. See the [published probe result](https://github.com/admiral-project/admiral/issues/307#issuecomment-6486556506) and retained log/script/guard under `runtime/centos-multi/`.
- **Effective SSH:** Admin, Worker and Portal CentOS R26 each had active `sshd`; global and validator-context `sshd -T` showed passwords and keyboard-interactive disabled, pubkeys enabled, and root login disabled or key-only. See the [published probe](https://github.com/admiral-project/admiral/issues/307#issuecomment-6486701478) and retained log/script/guard.
- **Podman/Quadlet:** App/DB containers had `NoNewPrivileges=1`, seccomp mode 2, private PID namespaces, `privileged=false`, and effective CPU/memory/PID limits. PostgreSQL had no effective capabilities; the app retained the OCI defaults required by some entrypoints. No OOM was induced. See the [Quadlet review](https://github.com/admiral-project/admiral/issues/307#issuecomment-6482164559).
- **Fleet and API boundaries:** Source review confirms Fleet's authenticated node scope, signed task verification, replay window, typed task actions, rootless execution path, path validation and cleanup failure handling. Customer API paths require ownership before queuing an operation. This is source review and CI evidence, not a live cross-tenant API attack test. See the [Fleet review](https://github.com/admiral-project/admiral/issues/307#issuecomment-6482234051) and [trust-boundary review](https://github.com/admiral-project/admiral/issues/307#issuecomment-6482312860).
- **Customer ownership handler test:** Focused Go tests passed against the exact R26 Admirald source for cross-customer lifecycle action, provisioning, operation lookup, backup list/read, and restore IDs. The forged-ID control is now supported at handler level; this is not a live cluster attack test. See `R26-CUSTOMER-OWNERSHIP-TEST.md`.
- **Customer lifecycle and backup authorization:** Handler tests reject cross-customer stop and backup/restore access, and accept a valid restore only for its route instance, authorized tier and selected service. The customer API has no delete/download method. These are handler-level tests, not live storage or cluster probes; see `R26-CUSTOMER-BACKUP-SCOPE-TESTS.md`.
- **Fleet failure and redaction tests:** Focused Go tests passed against the exact R26 source pins. They cover redaction of known secrets in Fleet command/inspect paths, failed executor results, and Admirald's persistence of failed callback status. See `R26-FLEET-ERROR-FAILURE-TESTS.md`.
- **Ansible baseline assertions:** R26 Fedora Admin/Worker/Portal logs show role-scoped public services/ports, dual-stack egress rules, forwarding disabled after WireGuard, effective audit rules, and an effective temporary Fail2ban nftables ban. The logs also show `no_log` output redaction. See `R26-ANSIBLE-BASELINE-ASSERTIONS.md`.
- **SELinux/systemd user:** SELinux was Enforcing in the R26 workload run; app/DB MCS labels differed and host control sockets were absent from the containers. Fedora Single R26 also rebooted with SELinux still Enforcing. Direct peer-unit control, shared-volume behavior, volume-path labels, AVC review and unit-failure impact were not tested. See the [SELinux/user-manager assessment](https://github.com/admiral-project/admiral/issues/307#issuecomment-6482358440).
- **Backup/restore:** The exact Fedora R26 Multi flow completed PostgreSQL backup, checksum-verified restore, resume, and deprovision. The original database marker returned after restore and temporary data was absent. This is direct lifecycle evidence for the tested PostgreSQL app, not a cross-tenant authorization test for backup endpoints.
- **Ansible baseline:** The R26 production playbooks completed and include effective assertions for SELinux enforcing, role-specific public ports/services, dual-stack egress policy, disabled IPv4/IPv6 forwarding, audit rules, and Fail2ban enforcement. Installer logs record those assertions and `no_log` redaction. This does not substitute for a separately captured post-install live snapshot of every host setting or an idempotence rerun.
- **Oct 29 follow-up:** Evidence supports eight additional checklist controls: Fleet setup commands are limited to trusted app definitions and run inside the target container; Fedora R26 retained SELinux Enforcing across a real reboot; security-update automation was installed, configured for security-only upgrades, and enabled; R26 Multi-Node used registered WireGuard routes and peers; Caddy on Admin routed strict-TLS Portal/workload traffic; the A/B probe found neither customer's PostgreSQL secret available in the other; the R26 S3 backup was checksum-restored with the original marker recovered; and exact-source task-signature, authorization-scope, and handler evidence passed in CI or focused tests. Limits for the source/handler checks are stated in R26-CHECKLIST-FOLLOWUP-20261029.md.
