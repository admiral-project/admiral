### Confirmed r4 product defect — Rawhide portal certificate (issue #140)

Issue [#140](https://github.com/admiral-project/admiral/issues/140) is a
regression of the closed [#128](https://github.com/admiral-project/admiral/issues/128).
The single-node/admin leaf signing path adds `subjectKeyIdentifier` and
`authorityKeyIdentifier`, but the portal-node controller-signed extensions file
(`ansible/roles/admiral_common/tasks/main.yml`, the portal temporary extensions
task) omits both. The resulting portal `admirald.pem` has no SKI/AKI, so
Rawhide's strict OpenSSL 3.5 client rejects the chain with
`Missing Authority Key Identifier`, and the customer cannot use the Harbor
portal. The role install, role audit and multi-node Golden lifecycle passed on
Rawhide; only the portal Harbor flow is FAIL. Applying the fix requires a new
pinned common commit, a coordinated six-RPM rebuild and a fresh matrix.

### Confirmed r4 product defect — Fedora worker clock check (issue #139)

Issue [#139](https://github.com/admiral-project/admiral/issues/139) records that
the secure `--worker-node` installation fails on Fedora 44 because the security
checklist samples `chronyc tracking` once, immediately after the playbook, and
aborts with `chronyd has not synchronized the system clock`. The Ansible recap
was `ok=143 changed=15 failed=0 unreachable=0` and the WireGuard handshake had
succeeded. `chronyc tracking` reaches `Leap status : Normal` about eight seconds
after the reconfigured state, so the check needs a bounded wait rather than a
single sample. The Fedora 44 multi-node cell is FAIL on this defect; the EL10
multi-node cells completed with the same candidate because their timing did not
leave the clock in the unsynchronised window. A bounded-wait or retry is the
proposed fix; no security control was relaxed and no source or RPM was changed
during this validation.
