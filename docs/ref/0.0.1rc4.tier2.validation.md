## Fedora Rawhide fix and r9 diagnostic evidence

Issue [#127](https://github.com/admiral-project/admiral/issues/127) reproduced
that Rawhide labels `/usr/bin/caddy` `httpd_exec_t`, but denied `httpd_t` a
TCP/2019 bind under SELinux enforcing. Commit `da0c03f` adds a secure Fedora 45+
conditional: when that executable label is present, it maps Caddy's loopback
admin port to `http_port_t`. It leaves SELinux enforcing and does not expose
Caddy's admin API beyond loopback. The fix is included in r10 `admiral-common`.

The r9 Rawhide single-node diagnostic install used the official 2026-09-23
image after `dnf update --refresh`; Ansible ended `ok=233 changed=104 failed=0`,
but Caddy stayed inactive and the installer exited 1. A later S3-configured
reconciliation ended `ok=203 changed=19 failed=0` but Harbor could not
authenticate because `admirald` was unreachable while Caddy was down. These
r9 guests are diagnostic only and have been shut down. The fix must be proven
on clean Rawhide single-node and all secure multi-node roles. Issue #126's
LLMNR condition is also included in the common source; keep it open until the
secure Fedora matrix passes.

The r10 Rawhide single-node diagnostic install proved the Caddy SELinux fix,
with no Caddy AVCs, but the installer still exited 1 during Harbor's
Admirald-reachability check. The Harbor Python client rejected the leaf
certificate because it lacked an Authority Key Identifier (`requests` reported
`Missing Authority Key Identifier`); strict OpenSSL verification reproduced
the same issue. Issue [#128](https://github.com/admiral-project/admiral/issues/128)
tracks it. The r11 certificate extensions fix this rejection. The clean
single-node rerun passed; the multi-node rerun remains required.
